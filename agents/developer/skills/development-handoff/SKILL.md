# 开发交接 Markdown

开发范围与人工审核/全自动执行模式是独立维度：

| 开发范围 | 本次实现 | 交接对象与内容 |
| --- | --- | --- |
| `joint` 联合开发 | 已绑定且获授权的前端、后端仓库 | 汇总两端实现、接口契约、联调证据及遗留项；交关联开发与测试 |
| `single/frontend` 单端前端 | 只改前端 | 将前端实际改动、接口依赖、需要后端实现的内容交给关联后端人员 |
| `single/backend` 单端后端 | 只改后端 | 将后端实际改动、接口契约变化、需要前端适配的内容交给关联前端人员 |

先采用用户指定范围，再采用工作区配置。联合开发须有两端仓库及权限；只有前端仓库不能声称完成后端，也不能擅自寻找并修改未授权仓库。若无法确定范围，先整理已有证据，再询问缺失信息。

## 生成内容

1. 读取适用仓库指令、任务原文、关联人员、实际 diff/提交、MR 和测试结果。以明确提交为依据，区分已实现、建议另一端实现、待确认；不将建议接口或模拟数据写成已上线事实。
2. 对涉及的接口列出方法、路径、字段类型、必填/可空、枚举、示例、错误处理及兼容性。只填有源码或文档依据的内容，缺失标注待确认。无需接口变更时明确说明，不编造另一端工作。
3. 使用下方结构写 UTF-8 `.md`。优先用户指定位置，否则写目标工作区 `docs/handoffs/{任务号}-{frontend|backend|joint}.md`。读取已有文件后更新对应版本，保留用户手写补充。生成文档不等于获准提交文档或推送仓库。
4. 联合任务分端记录提交及验证；单端任务只声明本端完成。另一端待实施、联调未执行、环境未部署等必须单独列出，不将本端构建成功写成端到端验收通过。

建议结构（无关小节可省略）：

```markdown
# 任务号 任务标题 — 开发交接

## 任务与交付范围
任务链接、开发范围、仓库、分支、提交 SHA、MR、当前阶段。

## 本次已完成
具体行为变化、影响页面/模块、关键文件及实现依据。

## 对端配合事项
每项描述现状、期望行为、接口/字段约定、建议负责人、依赖及验收方式。
区分必需实现、建议优化、待产品确认；没有配合项则写“无需对端代码变更”。

## 接口契约与示例
变更前后对比、请求/响应示例及来源。未知内容明确待确认。

## 验证与联调
已运行命令及结果、未验证事项、双方联调步骤与验收标准。

## 接收人与待确认事项
发送对象、需要对方回答的问题及当前交接状态。
```

## 测试交接文档

无论联合还是单端开发，在满足任务的提测条件并准备转交测试时，另生成 `docs/handoffs/{任务号}-test.md`，不以开发者交接文件替代。测试文档面向测试人员，以可操作步骤和可观察结果为主；模板如下：

```markdown
# 任务号 任务标题 — 测试交接

## 提测信息
任务链接、测试负责人、开发范围、MR、源提交及合并提交、提测时间。
目标环境与部署状态分别列出；合并 develop 不等于部署完成，未知写“待核实”。

## 改动与测试范围
用户可见的变化、影响页面/入口、接口或权限变化，以及本次不涉及的范围。

## 测试准备
可访问环境、账号角色、脱敏测试数据要求、功能开关、前后端依赖。
不提供真实凭证，不自动创建业务测试数据；数据库变更仍逐次确认。

## 测试用例
| 场景 | 前置条件 | 操作步骤 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- |
按真实需求填写主流程、边界、异常、权限和回归场景；不相关项省略。

## 回归重点
受影响的相邻功能、已有数据兼容性和需特别核对的旧行为。

## 开发自测与限制
实际执行的命令及结果、未执行的页面验证、模拟与真实联调的区别、已知问题。

## 验收与问题反馈
明确通过标准、阻塞项和建议反馈内容（步骤、期望/实际结果、截图、环境与版本）。
任务链接、关联开发人员及交接状态。
```

- 测试用例是待执行清单，不将生成用例写成测试已通过。已知阻塞和另一端未完成依赖应置于文档前部；整体不可测时仅保存草稿，继续走开发者交接，不提前标记提测成功。
- 优先采用任务已指定的测试负责人，否则使用工作区关联测试人员；多个候选且无明确规则时核对接收者，不广播。任务执行者变更后应读回确认实际测试负责人。
- 用户已要求任务交接时发给对应测试，即授权在该任务范围内发送测试交接。转测试时先生成文档、按既有规则回写并读回任务状态和执行者，再向核验身份的对应测试单聊交付文件或可访问链接，附任务号、改动摘要、测试重点与 MR。渠道不支持附件时沿用下方正文交付规则。
- 分别记录“任务已转测试”和“测试文档已发送”的状态。发送失败时保留待发送项并报告，不重复修改已成功的任务状态，不声称整个交接完成；不将已送达等同于已读或验收通过。

## 发送与状态

- 交接对象来自工作区关联角色：前端完成→后端；后端完成→前端；联合开发→关联开发和测试。优先任务已指定的对端负责人，否则使用用户明确绑定的对应角色人员；重名、人员无效或关联不明时先核对，不猜收件人。Teambition ID、钉钉 staffId 与 openDingTalkId 不可混用。
- 用户已要求单端开发完成后发给关联开发者时，这构成该范围的交接发送授权，无需每次重复询问。未授权的群广播、其他人员或其他项目不在范围内。通过已连接且足够的工具优先交付；工具审批要求照常保留。
- 开发 Agent 只生成文件和交接包；没有业务工具权限时将其交给钉钉 Agent。发送前核对接收者、任务/提交及文档内容，去除令牌、连接密码、真实客户敏感数据，示例使用占位值。
- 优先发送 Markdown 文件或已授权可访问的文档链接，同时附“改动摘要 + 对端待办 + MR”。本地路径不是对方可访问的链接；渠道不支持附件时发送分段 Markdown 正文并向当前用户提供本地文件。不能仅发送本地路径后声称文件已送达。
- 用任务ID、提交SHA、文档类型（开发/测试）、接收者和文档版本去重；记录实际消息ID/文件链接。发送失败或结果未知先查询对账，不盲目重发；报告“文档已生成，发送未完成”。发送成功不等于对方已读或已实现。
- 单端交接不自动改变另一开发者的任务状态。需要对端实现才能验收时，不直接标记整体任务开发完成并转测试；报告本端完成、等待对端配合。无需对端改动且满足现有交付条件时，沿用工作区已授权的转测试规则。
- 数据库变更仍须逐条 SQL 确认，DDL 保持禁用；把 SQL 写进交接文档不构成执行授权。
