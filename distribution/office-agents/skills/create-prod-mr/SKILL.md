# 创建生产环境 MR

在用户指定的 Git 仓库执行；未指定时使用当前工作目录所在仓库。创建 skill 本身不代表立即创建 MR。

## MR 规则

- 源分支：当前本地分支，保留完整分支名，包括 `feature/` 等前缀。
- 目标分支：每次执行时由用户指定完整分支名，不设固定值。不从日期、最新 release、仓库默认分支或历史 MR 自动推断。
- 标题：与源分支名完全相同，不添加任务号、前缀或其他文字。
- 描述：仅一行 `fix:{任务号}|{任务标题}|{任务链接}`，使用小写 `fix:` 和半角 `|`，分隔符两侧不添加空格，不添加 Markdown 标题或其他内容。

## 收集任务信息

执行时使用 `request_user_input_async` 一次弹出两个独立的文本输入问题：Teambition 任务号（例如 `TASK-123`）、生产 MR 的完整目标分支名。不提供选择项；当前请求已明确给出的字段直接复用，只询问缺失字段。没有弹窗工具时在聊天中一次询问缺失字段。不要默认从分支名或历史查询中选取任务。目标分支未明确前不得创建 MR。

目标分支去除首尾空白后使用 `git check-ref-format --branch` 校验名称，并从当前仓库的实际远程分支列表核对其存在。按字面值传递分支参数，不拼接为 shell 代码。分支不存在时请用户修正，不自动创建目标分支，不改用其他分支。

去除首尾空白，按“项目前缀-数字编号”解析任务号。保留实际项目的前缀，不将分支后缀（如 `_2`）当作任务号。格式不符时追问，不猜测。

默认使用已连接的 Teambition 官方 MCP 仅读取任务信息，不修改任务状态、评论或其他业务数据。

1. 首次使用或不了解查询方式时，先调用 `teambition.docs.search`，再调用 `teambition.docs.get` 阅读 `task/tql` 或搜索结果中的相关文档。
2. 根据项目前缀确认项目，再在项目内按数字编号查询。从当前工作区绑定或用户指定范围确认项目 ID、编号前缀与访问权限，不复用其他项目的 ID。
3. 使用 `teambition.project.task-query`，传入确认的 `projectId` 和 `tql: "uniqueId = 123"`（数字替换为实际编号）。任务标题取返回的 `content`，链接标识取同一条任务的 `projectId` 和 `taskId`/`id`；核对 `uniqueId` 与输入一致。
4. 优先使用接口返回的任务网页 URL；没有 URL 时，对 Teambition 公有云使用实际 ID 组成 `https://www.teambition.com/project/{projectId}/tasks/{taskId}`。私有部署须从实际网页或部署配置确认域名。不要把 API URL、关联链接或 OAuth 地址当成任务链接，也不要声称拼接的链接已通过浏览器验证。
5. 查询唯一匹配后，展示任务号、任务标题和链接，并用于 MR 描述，无须再弹窗要求用户抄写或确认已查到的字段。多个匹配时让用户选择；成功返回空结果时说明未找到。权限、连接或参数错误不能当作任务不存在；读取文档后至多进行一次有明确依据的参数修正，不删条件扩大查询。

MCP 不可用或查询不到任务时，说明具体原因，弹窗请用户修正任务号，或手动提供任务标题和完整 HTTP/HTTPS 任务链接；也可读取用户提供的已登录任务网页。任务信息未齐全前不得创建 MR，不编造标题或链接。

最终三个字段不得为空或含换行、`|`；任务标题含这些字符时说明格式冲突并请用户提供用于 MR 的单行标题，不静默改写任务标题。

## 创建流程

1. 读取当前仓库、分支、工作区状态和远程地址，确定 GitLab 项目。以实际仓库 remote 和工作区绑定核验目标实例。多个可能的远程存在歧义时让用户指定，不跨项目创建。
2. 分支为 detached HEAD、当前分支与用户指定的目标分支相同、目标分支不存在或没有差异可合入时，说明具体原因并停止创建。读取远程状态时先刷新相应引用，失败则说明验证限制。
3. 查找同一项目中源分支到用户指定目标分支 的已打开 MR。已有时返回链接，核对标题和描述；若不符合规则，展示具体差异并询问是否更新已有 MR，避免重复创建。
4. 检查当前分支提交是否已推送。用户要求创建 MR 时，可以推送当前分支已存在的提交并设置对应 upstream；仅使用普通 push。不要自动提交工作区改动、强制推送、重置分支或更改已有远程跟踪关系。未提交的改动需说明不会包含在 MR 中。普通 push 被拒绝时报告原因，不自行变基或覆盖远程。
5. 生成并展示具体的项目、源分支、目标分支、标题和单行描述。用户要求执行本 skill 创建 MR 即授权按这些规则创建，无须增加重复确认步骤。
6. 优先使用已安装并认证的 GitLab CLI `glab`，通过 API 创建 MR，不打开浏览器。先用 `glab auth status --hostname <远程主机>` 验证 API 登录；Git 凭据可用不代表 glab API 认证可用。从 PATH 查找 glab，不使用其他机器的绝对安装路径。使用 `mr list --source-branch <源分支> --target-branch <用户指定的目标分支> --output json` 查重；使用 `mr create --source-branch <源分支> --target-branch <用户指定的目标分支> --title <完整分支名> --description-file <UTF-8临时文件> --yes` 创建。描述文件用 UTF-8 无 BOM 写入完整单行描述，避免将用户输入拼接为 shell 命令。可使用已连接且支持该实例的 GitLab API 工具作为替代。缺少 glab、连接或登录时说明具体缺口，不自动打开浏览器，不读取或输出令牌。
7. 创建普通 MR，保持用户指定的目标分支，不执行合并、自动合并、部署、删除源分支、指派评审或向其他人发送消息。创建失败或超时后先查询是否已成功创建，再决定是否重试，避免重复 MR。
8. 创建成功后再次读取确认源分支、目标分支、标题和描述符合上述规则，若当前环境支持 attach_artifact，可将 MR URL 附加到聊天；否则返回普通可点击链接。返回可点击的 MR 链接和简短结果，同时如实说明已知的冲突和流水线状态；不自动修复合并冲突。
