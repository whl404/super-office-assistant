# 工作流、状态与恢复

## 当前可装配流程

当前 [五条工作流模板](../config/workflows.json) 已可由 [持久化调度器](scheduler.md) 加载和执行，支持依赖、工具循环、批准等待、产物及验收；真实模型和业务客户端尚未注册。GitLab 已暂停，下面的 MR 流程暂不可执行；不会自动换用 GitHub 或降低验收标准。

办公查询走“理解→只读查询→直接回答”，不建任务、不额外发送通知。文档建任务走“读取资料→拆解→在指定项目创建→读回核验→返回任务链接”。本地代码交付不推断 MR 或 CI 成功。

## 标准研发流程

| 阶段 | 负责者 | 输入 | 输出与推进条件 |
| --- | --- | --- | --- |
| 接入 | 事件入口 | 原始事件 | 验证来源、绑定身份、去重，建立或定位运行 |
| 资料收集 | 钉钉 Agent | 指令、文档引用 | 需求资料、来源版本、缺失项 |
| 分析规划 | 统筹 Agent | 资料、项目映射 | 范围、验收标准、任务 DAG；关键缺失项先询问 |
| 任务落地 | Teambition Agent | 计划、已有任务 ID | 关联已有任务或按策略新建，记录映射 |
| 仓库定位 | GitLab Agent | 项目及仓库范围 | 仓库 ID、基础分支与 SHA、相关 MR |
| 实现 | 开发 Agent | 需求、基础 SHA、任务 ID | 独立分支、提交 SHA、差异、测试证据 |
| 本地验收 | 评审 Agent | 确定的提交与验收标准 | 通过、需修改或证据不足，逐项说明 |
| MR 与 CI | GitLab Agent | 已评审提交、交付说明 | 创建/更新 MR，等待当前 head SHA 对应 CI |
| 交付判定 | 统筹 Agent | 评审、MR、CI 证据 | 达到 MR 交付标准；失败时返工或报告阻塞 |
| 状态回写 | Teambition Agent | 实际交付事实 | 业务任务进入项目配置的待评审状态 |
| 汇报 | 钉钉 Agent | 交付摘要和链接 | 原会话通知、消息 ID |

CI 失败时：GitLab Agent 收集当前提交的失败证据，统筹安排开发修复；新提交重新评审并重新等待 CI。不得沿用旧 SHA 的通过结果。无 CI 的仓库是否允许以本地验证替代，必须由项目策略明确，默认 CI 未配置意味着证据不足。

文档查询等任务只调度必要角色，可跳过 Teambition/GitLab；是否建任务由项目策略确定。

## 运行状态

| 状态 | 含义 | 可转入 |
| --- | --- | --- |
| `received` | 接入并保存 | `analyzing`, `cancelled` |
| `analyzing` | 收集上下文、澄清目标 | `waiting_input`, `planned`, `blocked`, `failed`, `cancelled` |
| `waiting_input` | 等待原用户补充，记录恢复点 | 原恢复状态、`cancelled` |
| `planned` | 当前计划可执行 | `executing`, `analyzing`, `cancelled` |
| `executing` | 子任务执行 | `verifying`, `waiting_input`, `waiting_authorization`, `blocked`, `failed`, `cancelled` |
| `verifying` | 评审及 MR/CI 验证 | `executing`, `syncing`, `waiting_input`, `waiting_authorization`, `blocked`, `failed`, `cancelled` |
| `waiting_authorization` | 某动作超出现有授权或工具要求确认 | 原恢复状态、`cancelled` |
| `syncing` | 交付条件满足，回写及通知尚未完成 | `delivered`, `waiting_authorization`, `blocked`, `failed`, `cancelled` |
| `blocked` | 已知依赖、能力或证据缺失 | 问题解决并核验后恢复到记录状态，或 `cancelled` |
| `failed` | 无法自动恢复的运行故障 | 终态；显式重开生成关联的新运行 |
| `cancelled` | 用户取消或执行期限到达 | 终态；迟到结果仅记账，不推进 |
| `delivered` | 所选工作流的验收与必要回写完成；MR 仅适用于研发扩展 | 终态；合并/发布由独立跟踪流程处理 |

等待状态不占用工作进程。`resume_state`、等待原因、预期回复者、问题 ID、期限持久化；默认 24 小时后提醒一次，72 小时后转 `blocked`，不因超时推断同意。试点阶段可按项目修改期限。

操作批准已映射到 waiting_authorization，持久保存 approval_id。后台 serve 会在批准后以原逻辑键继续；拒绝、撤销或过期不执行。单次批准默认 15 分钟，不因等待自动续期。此处 24/72 小时提醒属于后续渠道策略，当前调度器不自动发送提醒。

子任务状态独立为 `pending / ready / running / waiting / succeeded / failed / blocked / cancelled`。只有前置依赖成功、计划版本仍有效且授权满足时才能进入 `ready`。

## 外部状态映射

Teambition 状态由项目配置的实际状态 ID 映射：计划建立→待处理，开始实现→进行中，MR 交付→待评审，合并/发布→项目约定的后续状态。不得假定每个项目都有相同名称或以 MR 创建代替任务完成。

GitLab 保留 MR 状态、head SHA、pipeline ID、pipeline SHA 与状态。CI 等待每次默认最多 30 分钟，超过后转阻塞等待外部事件或对账；不持续占用模型调用。

## 重试与返工

- 只读查询的瞬时网络错误最多重试 3 次，退避 2/5/15 秒并加抖动；遵守服务端限流等待时间。
- 写入超时标记为 `unknown`，先按操作记录查询真实结果。能够确认未执行才重试；无法确认时阻塞对账。
- 权限不足、资源不唯一、无效参数和验收歧义不做机械重试。
- 自动返工默认最多 2 轮，开发与评审/CI 共享该运行计数；超过后汇总已完成内容及失败证据。
- 预算和执行时限由引擎计数；达到预算转 `blocked`，用户明确扩充后恢复。执行期限到达则取消，已产生的产物仍保留。

## 去重与恢复

入口去重键为组织、来源、事件 ID 的组合。回复先关联 `question_id` 或运行会话，不当作新需求。Teambition/GitLab 回写保存关联标记、对象版本和操作记录，以动作类型及实际字段变化过滤自身回调，避免循环触发。

外部动作先保存 `operation_id`、幂等键、目标、参数摘要、授权快照及 `pending` 状态，再执行并保存结果。服务不支持幂等键时，通过对象关联标记和查询对账；具体查询策略由适配器定义。

进程崩溃后重新取得任务租约，使用 fencing token（递增租约代号）阻止旧进程继续更新状态；查询未决写入结果再续跑。状态更新使用版本校验；事件和待发送消息使用本地事务/outbox 一并保存。

同一业务对象的写入按资源 ID 串行。不同代码任务使用独立工作目录，集成后生成新 SHA，必须重新验证。

## 用户改需求与取消

补充信息若影响范围或验收，生成新 `plan_version`；旧版本任务停止调度。对运行中任务发出取消信号，隔离迟到结果，并查询已发出的外部操作是否成功。

取消不自动删除分支、MR、任务或已发消息。记录已有产物并向用户反馈；确需清理时按照该对象的授权策略执行。需要人工批准的动作暂停于 `waiting_authorization`，已有授权范围内的动作继续。
